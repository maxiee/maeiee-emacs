* 这套配置要解决什么

这不是一份“复制完就结束”的豪华配置，而是一套会随着学习一起生长的系统：

1. Org 文件是唯一的人类可维护配置源码；
2. 每个 Org 文件讲一种稳定能力或一条完整工作流，不按小插件机械拆分；
3. Org 标题解释组成角色，源码块保留具体配置与加载时机；
4. 保存模块时自动 tangle，启动时只加载生成的 Elisp；
5. 一个极小的 =init.el= 负责找到 Git 仓库；
6. =bootstrap.sh= 把任意新安装的 Emacs 接到仓库。

核心原则：*先理解，再加入；能用内置，就暂缓插件；每次只改变一件事。*

* 第一阶段：在 macOS 安装 Emacs

** 安装 Homebrew

若尚未安装 Homebrew，请从 Homebrew 官方站点复制当前安装命令。安装后确认：

#+begin_src shell :tangle no
brew --version
#+end_src

** 安装稳定 GUI 版 Emacs

#+begin_src shell :tangle no
brew install --cask emacs-app
#+end_src

确认：

#+begin_src shell :tangle no
/Applications/Emacs.app/Contents/MacOS/Emacs --version
#+end_src

不建议刚开始就使用 nightly，也不建议为了某个补丁立刻切到复杂的第三方构建。先让学习材料、配置结构和操作习惯稳定下来。

* 第二阶段：创建 Git 仓库

下面以 GitHub 为例，GitLab 或自建 Git 服务完全一样。

#+begin_src shell :tangle no
mkdir -p ~/Code
cd ~/Code
mkdir maeiee-emacs
cd maeiee-emacs
git init
#+end_src

把本 starter 的文件放入目录后：

#+begin_src shell :tangle no
git add .
git commit -m "chore: bootstrap literate Emacs configuration"
git branch -M main
git remote add origin git@github.com:YOUR_NAME/maeiee-emacs.git
git push -u origin main
#+end_src

仓库可以是私有的。不要把密码、Token、公司路径写进模块。需要在模块加载前生效的机器特有内容放在 =~/.emacs.d/early-local.el=，普通机器特有覆盖放在 =~/.emacs.d/local.el=；这两个文件都不属于仓库。

只有本仓库的 =modules/*.org= 会在缓冲区内跳过 Babel 执行确认；普通 Org 文档继续保留确认提示。不要对来源不明的 Org 文件随意执行源码块。

* 第三阶段：自举新机器

在另一台 Mac 上：

#+begin_src shell :tangle no
mkdir -p ~/Code
cd ~/Code
git clone git@github.com:YOUR_NAME/maeiee-emacs.git
cd maeiee-emacs
./bootstrap.sh --install-emacs
#+end_src

脚本会：

1. 找到或安装 Emacs；
2. 备份旧 =~/.emacs=、=~/.emacs.el=、=~/.emacs.d/init.el=；
3. 把 =early-init.el= 和 =init.el= 链接到仓库；
4. 批量 tangle 所有模块；
5. 保留软件包、缓存、Custom 数据在 =~/.emacs.d/=，不污染 Git 仓库。

它不会删除旧配置；冲突文件会加时间戳备份。

* 第四阶段：第一次启动

从 Finder 打开 Emacs，或运行：

#+begin_src shell :tangle no
open -a Emacs
#+end_src

第一次启动会刷新 package archive，并按模块需要安装 Evil、Vertico、Magit 等软件包。网络失败时先检查 =*Messages*=，再执行：

#+begin_example
M-x package-refresh-contents
M-x package-install-selected-packages
#+end_example

** 为不同机器配置本地代理

如果本地 HTTP 代理在不同机器上使用不同端口，不要把端口提交进公共模块。复制仓库提供的早期本地配置示例：

#+begin_src shell :tangle no
cp bootstrap/early-local.example.el ~/.emacs.d/early-local.el
#+end_src

然后只修改本机文件中的端口：

#+begin_src emacs-lisp :tangle no
(setq maeiee-proxy-port 7890)
#+end_src

例如另一台机器可以改为 =7897=。=early-local.el= 会在 =00-package.org= 之前加载，因此 =package-refresh-contents= 与 =use-package= 安装依赖时都会使用代理；随后加载的 =local.el= 仍可用于普通的机器级覆盖。

如果 Emacs 已经停在 =Contacting host=，先退出 Emacs、创建上述文件并确认代理程序正在运行，然后重新启动。首次索引刷新成功后会写入 =~/.emacs.d/var/package-archives-ready=，以后不会在每次启动时重复刷新。

基础诊断：

#+begin_src shell :tangle no
./scripts/doctor.sh
make check
#+end_src

若 =make= 找不到正确 Emacs：

#+begin_src shell :tangle no
make EMACS=/Applications/Emacs.app/Contents/MacOS/Emacs check
#+end_src

* 每天怎样维护

** 阅读

从 =00-package.org= 开始，一次只读一个模块。每章包含目标、概念、配置、验证和维护笔记。

** 修改

不要编辑 =generated/*.el=。只改 =modules/*.org= 中的 Emacs Lisp 源码块；保存
或检查时重新生成对应 Elisp，并把源码与生成文件成对提交。

** 保存与应用

保存模块时自动 tangle。要立即在当前会话应用：

#+begin_example
M-x maeiee-reload-current-module
#+end_example

也可进入配置管理二级菜单，再点击“重载当前模块”：

#+begin_example
SPC m
#+end_example

要打开文学配置文件，在这个面板中点击“查找配置文件”，再从补全列表选择
README、bootstrap、ROADMAP 或当前任一模块。模块列表来自实际的 =modules/=
目录，因此文件增删或改名后不需要维护另一份菜单清单。

注意：重载配置不总能撤销旧副作用。改 hook、keymap、mode 时，偶尔重启 Emacs 是最可靠的验证。

** 提交

#+begin_src shell :tangle no
git status
git diff
git add modules/XX-topic.org generated/XX-topic.el
git commit -m "feat: explain and configure topic"
git push
#+end_src

一次提交只解决一个学习主题。这样 Git 历史本身也是你的学习轨迹。

* 键位设计

本 starter 使用三层键位：

1. *Evil 编辑层*：=h/j/k/l=、=d/y/p=、text object 等；
2. *Leader 命令层*：=SPC f= 文件、=SPC b= 缓冲区、=SPC p= 项目；=SPC m= 进入可点击的 Maeiee 配置管理二级菜单；
3. *macOS 兼容层*：⌘S、⌘O、⌘F、⌘C、⌘V、⌘Z。

同时保留 Emacs 原生键：

- =M-x=：按名字执行命令；
- =C-h=：帮助系统；
- =C-g=：中止当前操作；
- =C-x C-s=：保存；
- =C-x C-f=：打开文件。

不要试图第一天“统一掉所有 Emacs 键”。原生键是阅读文档和排错时的公共语言。

* 建议的学习路线

** 第 1 周：只学编辑器的自解释能力

- =C-h k=：这个键做什么；
- =C-h f=：这个函数做什么；
- =C-h v=：这个变量做什么；
- =C-h m=：当前 major mode 是什么；
- =M-x=：按名字探索命令；
- =M-:=：临时求值一段 Elisp。

目标不是背键，而是学会在 Emacs 内部自己找答案。

** 第 2 周：Org 与文学配置

- 标题折叠、列表、链接；
- 源码块与 =C-c '=；
- =C-c C-v t= tangle；
- =C-c C-e= export；
- 理解“文档源码”和“机器产物”的边界。

** 第 3 周：Evil 与 Leader

- state、operator、motion、text object；
- leader 的命名空间；
- 只给高频动作分配快捷键；
- 用 which-key 发现，而不是背整张表。

** 第 4 周：minibuffer 与项目

- 把补全理解为一条协作链：Vertico 展示、Orderless 匹配、Marginalia 注释、
  Consult 提供带预览的命令；
- project.el 定义项目协议，Treemacs 把同一项目呈现为文件树；
- Magit 是 Git porcelain。

* 如何规划和拆分模块

模块采用三级口径：

#+begin_example
Org 文件      = 稳定能力、完整工作流或确有独立生命周期的子系统
二级标题      = 组成角色、工作阶段或具体插件
Emacs Lisp 块 = 配置实现与加载时机
#+end_example

例如，Embark 是 Minibuffer 候选动作层，应成为 =40-minibuffer.org= 的一个主题；
Corfu 与 Cape 服务编辑缓冲区内补全，应进入 =70-programming.org=；Dart 与 Flutter
初期也先作为程序开发主题。Capture、Agenda、Refile、Archive 形成真实的收集到
归档流程后，可以共同建立 =81-org-workflow.org=，而不是各占一个小文件。

判断是否真的需要新建文件时，依次做四个测试：

- *替换测试*：更换实现插件后，文件名和本章目标是否依然成立？
- *共同变化测试*：其中的组件是否通常一起启用、调整和验证？
- *独立生命周期测试*：它是否确实需要独立加载、重载、禁用或回滚？
- *完整章节测试*：能否围绕一个用户问题写出目标、概念、配置和端到端验证？

满足独立生命周期并通过其他测试时，才适合建立新模块。单个 =use-package= 或几十
行代码通常应先成为既有模块的标题；反过来，文件很长也不自动意味着需要拆分，
只要它仍在解释一条连贯工作流。文件名前的两位数字继续承担真实加载顺序，不应
只为了视觉分组随意调整。

* 发生故障时的最短路径

1. 用 =emacs -Q= 判断是不是个人配置导致；
2. 看 =*Messages*=；
3. 运行 =M-x toggle-debug-on-error= 后重现；
4. 运行 =./scripts/doctor.sh=；
5. 运行 =make check=；
6. 把最近一个模块暂时改名为不以两位数字开头，验证是否恢复；
7. 用 Git 回退最近一次小提交。

不要在错误状态下连续安装十个包。先缩小问题边界。
